## 1. 背景与问题

P14 已把「对外取数」从「匿名公开窗」修订为「授权取数面」：数据应用 →（`disp_grant` 授权）→ 展示应用 →（`site_id` 挂靠）→ 站点，站点展示页经同源相对路径 `/api/open/:slug/api/app/:appCode/**` 取数，服务端按 R125 四步链逐级放行。该机制解决了**跨站点隔离**（别人的站点拿 `appCode` 也读不到我的数据），但交付后澄清出两个此前未讨论的边界：

1. **授权粒度止于站点**：取数 URL 不含 `displayId`，判定是「该站点下**任一**挂靠展示应用被授权」即放行 → 同站点下另一个未授权的展示应用，其页面也能调同一接口。
2. **匿名层不可管控**：开放层全 `@Public()`、无凭证/无 Origin 校验。一旦某站点下存在被授权的展示应用，**任何来源**（curl、他站页面、爬虫）请求该站点路径都能在限流内读到数据。即语义是「该站点公开可读」，不是「仅该应用可读」。

与此同时，用户提出平台后续要支撑两个新场景：**对外开放给特定外部系统访问数据**、**对外提供 AI MCP（Model Context Protocol）能力**。这两个场景的调用方都不是匿名公众——它们需要**身份、范围、配额、审计**。

**结论**：这不是「给 P14 打补丁」，而是把对外访问从「站点 = 唯一隐式主体」升级为**「多主体 + 凭证 + 范围授权 + 审计」的统一接入层**，站点只是其中一种主体。匿名层应被明确定位为「公开数据」，管控型访问一律走凭证。【建议】

### 2.2 边界与「防住/没防住」

| 场景                                               | 现状结论                                                         |
| -------------------------------------------------- | ---------------------------------------------------------------- |
| 他人站点拿我的 `appCode` 直读                      | **防住**：其 slug 下无对应授权边 → 40400                         |
| 他人拿我的 `displayId` 走他的站点取我的展示文件    | **防住**：`resolveForOpen` 要求 `site_id` = 该 slug 站点 → 40400 |
| 同站点内另一个未授权展示应用调同一接口             | **没防住**（边界 1：粒度站点级）                                 |
| 任何人（curl / 他站 / 爬虫）请求我的站点路径读数据 | **没防住**（边界 2：匿名可达）                                   |

### 2.3 核心判断【建议】

**匿名层只能表达「公开数据」，不应承载「管控」。** 在公开站点上做「防盗链式」加固（Origin/Referer、页面注入短期 token）都只是提高门槛：页面能拿到的凭证，攻击者同样能拿到。真正需要「仅特定调用方」的场景，必须引入**显式凭证**。据此把两类访问分治：

| 访问类型               | 定位                             | 信任模型       | 手段                                  |
| ---------------------- | -------------------------------- | -------------- | ------------------------------------- |
| 站点展示页取数（现状） | **公开数据**（等同网站公开内容） | 站点即公开边界 | 匿名 + 授权链 + 限流 + 敏感字段不暴露 |
| 外部系统对接（新）     | **管控数据**                     | 凭证即身份     | 凭证 + 范围授权 + 配额 + 审计         |
| AI MCP（新）           | **管控数据**（客户端形态）       | 同外部系统     | 复用同一凭证体系，仅换协议适配器      |

## 3. 需求方向（用户口径）

| #   | 方向                 | 调用方                       | 核心诉求                                                           |
| --- | -------------------- | ---------------------------- | ------------------------------------------------------------------ |
| ①   | 对外特定系统访问数据 | 第三方系统（服务端到服务端） | 凭证化接入、能限定可读范围、可吊销、可统计                         |
| ②   | AI MCP               | AI 客户端 / 模型             | 数据应用以「工具 + 结构描述」形态暴露，模型可自解释调用            |
| ③   | 未来可扩展           | ——                           | 再加接入方式时**不改数据层**（新接入 = 新凭证解析器 + 协议适配器） |

方向①②的共同点：**调用方不是匿名公众**，因此必须回答「谁在调、能读什么、读了多少、如何停掉」。方向③要求模型层面先做好抽象，否则每加一个场景都要改 URL 与校验链。

## 4. 目标模型（建议）

### 4.1 设计原则

| #   | 原则           | 说明                                                                   |
| --- | -------------- | ---------------------------------------------------------------------- |
| P1  | 主体与凭证分离 | 「谁」（主体）与「如何证明」（凭证）解耦，同一主体可换凭证类型         |
| P2  | 授权即数据     | 授权关系落表（含范围与有效期），不写代码分支                           |
| P3  | 单一取数管道   | 所有接入方式共用同一取数门面；新接入只加「凭证解析器 + 协议适配器」    |
| P4  | 对外契约冻结   | 对外输出带版本号，对外字段名与内部逻辑字段解耦（内部重构不改对外契约） |
| P5  | 平台级横切     | 配额与审计做成平台能力一次，不在各接入方式里各做一套                   |

### 4.2 四件套

```
请求 ──► 凭证解析 PrincipalResolver ──► principal {type, id, ownerId}
                                          │
                                          ▼
                        范围授权 grant(principal → app, scope)
                                          │
                              is_public=1 → 表/字段暴露 → 取数执行器
                                          │
                                          ▼
                              审计 audit（谁 / 何时 / 哪表 / 多少行 / 结果码）
```

| 件                  | 内容                                                                                                                                             | 与现状关系                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| **主体 principal**  | `site`（匿名站点页，保留）/ `display`（展示应用）/ `system`（外部系统）/ `mcp`（MCP 客户端）                                                     | 现状隐式为 `site`，需显式化                          |
| **凭证 credential** | `anonymous`（无凭证，仅 site 场景）/ `api_key`（key_id + secret hash，可吊销·轮换·过期）/ `oauth_token`（client_credentials，视 MCP 客户端要求） | 全新                                                 |
| **授权 grant**      | `(principal_type, principal_id, app_id, scope)`；`scope = { ops, tables, fields, rowFilter?, expiresAt? }`                                       | 现状 `disp_grant(app_id, display_id)` 布尔授权的泛化 |
| **审计 audit**      | principal、appId、table、参数摘要、结果行数、耗时、IP、结果码                                                                                    | 全新（外部对接的准入前提）                           |

### 4.3 落地口径

- **判定入口统一**：`assertCanRead(appId, siteId)` → `assertCanRead(appId, principal)`；`site` 主体先按现状反查（行为零变化），新主体按凭证解析。【建议】
- **数据层零改**：取数仍经 `AppFacade` 现有四方法（`publicSchema` / `publicList` / `publicDetail` / `publicAttachment`）；新接入只是多一个调用方。**绝不新开直读表的通道。**
- **配额口径从 IP 改为 principal**：现有 60 次/分/IP 保留（防爬），新增按 principal 的请求数与行数配额（MCP 客户端会显著放大请求频次，按 IP 会误伤也多绕）。
- **敏感面仍由暴露三开关兜底**：`scope` 只能**收窄**（暴露开关的并集内），不能越过 `is_exposed=0`。

## 8. 非目标与风险

**非目标**：对外写数据（Q1 结论前）；按量计费与账单；凭证的市场分发（市场条目仍只复制数据应用与展示应用，不带对外凭证）；跨属主授权；匿名层 token 化（除 Q6 采纳 b）；行级授权实现（仅预留）。

**风险与对策**：

| 风险                               | 对策                                                                   |
| ---------------------------------- | ---------------------------------------------------------------------- |
| 凭证泄露                           | 密钥仅创建时展示一次、支持轮换与吊销、前缀可辨识便于溯源、异常用量告警 |
| MCP 放大查询频次（模型反复试参数） | 配额按 principal 而非 IP；工具描述限制参数范围                         |
| 对外契约随内部重构漂移             | 契约冻结层 + 版本号（Q7）                                              |
| 开放层被当爬虫目标                 | 现有限流保留；公开数据范围与敏感字段由暴露三开关收口                   |
| 接入方式增多后判定逻辑分叉         | P3：单一管道 + 主体化判定入口，新增只加解析器与适配器                  |
