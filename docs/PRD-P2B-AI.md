## 1. 需求背景

P2a 的 AI 只会聊天：不懂平台怎么用（"如何添加角色权限"答不上），也没有操作能力（"查在线人数""踢人下线"做不到）。P2b 补两块：

1. **平台知识**：AI 能准确回答平台各功能的位置与操作方法
2. **工具调用**：AI 能通过 Function Calling 调用系统业务 Service，完成查询类操作（自动执行）和写操作（确认后执行）

## 2. 范围

## 3. 功能细则

### 3.1 第一批工具清单（7 个）

| 工具名            | 说明                          | 级别  | 绑定权限           | 备注                                                                             |
| ----------------- | ----------------------------- | ----- | ------------------ | -------------------------------------------------------------------------------- |
| get_online_users  | 查询当前在线用户列表与数量    | read  | system:online:list |                                                                                  |
| kick_user         | 将指定用户踢下线              | write | system:online:kick | 参数 username；不可踢 admin 和自己                                               |
| search_users      | 按用户名/状态模糊查询用户列表 | read  | system:user:list   | 返回前 20 条摘要字段                                                             |
| list_roles        | 查询角色列表（含标识与状态）  | read  | system:role:list   |                                                                                  |
| get_my_profile    | 查询当前用户自己的资料        | read  | 无（登录即可）     |                                                                                  |
| update_my_profile | 修改当前用户自己的资料        | write | 无                 | 仅限 nickname/email/phone/gender；handler 强制 userId = 当前登录人，禁止从参数传 |
| get_my_credits    | 查询当前用户的套餐与积分用量  | read  | 无                 |                                                                                  |

### 3.2 工具调用主流程

```
用户消息 → 后端按"当前用户有权限的工具"组装 tools（模型 support_tool=1 才携带）
→ 上游返回 tool_calls：
   ├─ read 工具：立即执行 → 结果以 role=tool 回喂上游 → 继续流式输出最终回答
   │   （前端同时收到 tool_result 折叠标签："已查询在线用户"）
   └─ write 工具：不执行 → SSE 下发 tool_confirm 事件 → 前端渲染确认卡片
       → 用户点"确认执行" → POST /ai/tool/confirm（SSE 返回模型总结，作为新的 assistant 消息追加并独立结算）
       → 用户点"取消" → 记录 rejected，回喂模型"用户已取消"，模型自然语言回应
```

### 3.3 安全与边界规则

1. **权限双保险**：下发给模型的工具列表按用户权限过滤（没有的工具模型根本不知道存在）；执行时后端再校验一次权限（防权限间隙变化）
2. **工具调用轮次上限 3**：一次用户消息最多触发 3 轮工具调用，防模型循环调用烧积分
3. **确认单**：write 工具生成确认单存 Redis（`ai:confirm:{toolCallId}`，TTL 10 分钟），过期/重复提交返回 20016
4. **确认接口也做 SSE**：确认/取消后模型需要输出后续自然语言，复用同一渲染通道
5. **计费粒度**：read 场景一轮内多次上游调用（工具回喂续调）累加进同一条 assistant 消息统一结算；write 确认后的模型总结是**新的 assistant 消息、独立结算**（confirm 接口前置做套餐/积分预检，不足返回 20001/20002；与 /ai/chat 共用并发流锁，冲突返回 20007）
6. **工具执行不绕过业务规则**：handler 复用对应域已暴露的 Service（与普通接口同规则），禁止在 handler 里写旁路逻辑
7. **留痕**：每次工具调用写 ai_tool_call（工具名、参数、状态 pending/confirmed/rejected/executed/failed、结果摘要）
8. **手册同步纪律**：任何功能模块上线/变更，必须同步更新 docs/PLATFORM-GUIDE.md（写入 AGENTS.md 收尾动作）

### 3.4 平台知识问答

- system prompt 结构（后端拼装，顺序固定）：
  1. 助手设定（你是 iplat 平台内置 AI 助手……）
  2. docs/PLATFORM-GUIDE.md 全文
  3. 当前用户上下文：昵称、角色名列表、当前日期
- 手册维护：面向 AI 阅读编写，只写"是什么、在哪、怎么操作、有什么限制"，控制在 2000 字内；功能变化时同步更新
- 模型不知道答案时应引导用户查看具体菜单，禁止编造操作路径
- **成本认知**：手册全文每轮对话都计入输入 tokens（约 2k tokens/轮），属预期开销，模型单价录入与用量展示需有此预期；DeepSeek/Kimi 等厂商的 prompt 缓存会自动降本

### 3.5 前端交互

- **确认卡片**：标题（动作中文名）+ 参数摘要（key-value 表格）+ 确认执行/取消按钮；10 分钟过期后按钮置灰显示"已过期"；已处理的卡片固化为"已执行/已取消"状态
- **工具结果标签**：AI 消息上方折叠标签，如"🔍 已查询在线用户"，点击展开看原始数据摘要
- **确认后输出**：确认接口的 SSE 流渲染为**新的 AI 消息气泡**（不续接到卡片所在消息）
- **刷新恢复**：重新打开会话时，历史确认卡片按消息 item 携带的 toolCalls 数组固化渲染（已执行/已取消/已过期置灰），不得消失
- **模型选择器**：support_tool=1 的模型显示"支持工具"标记；当前模型不支持工具时，对话区顶部提示"该模型不支持工具调用"

## 5. 验收标准

- [ ] 问"如何添加角色权限"，回答路径与实际菜单一致（系统管理→角色管理→新增→分配权限），不编造
- [ ] admin 问"现在有多少人在线"，AI 自动调工具并给出真实人数与列表
- [ ] admin 说"把 tester 踢下线"，弹出确认卡片；确认后 tester 下一请求回登录页；取消则 AI 回应已取消
- [ ] 普通用户（无 system:online:kick 权限）说"把 tester 踢下线"，AI 明确告知无权限，且不产生确认卡片
- [ ] 普通用户说"修改我的昵称为小明"，确认卡片确认后个人资料页可见变更；尝试改他人资料被兜底拦截
- [ ] 每次工具调用在 ai_tool_call 留痕，状态流转正确（pending→confirmed/rejected/executed）
- [ ] 工具调用场景积分正常扣减（多次上游调用合并计费），usage 明细可查
- [ ] support_tool=0 的模型对话行为与 P2a 一致（不携带工具）
- [ ] 确认单 10 分钟过期后点击确认返回 20016
- [ ] 含确认卡片的会话刷新页面后，卡片状态正确恢复（已执行/已取消固化展示）
- [ ] 确认后的模型总结为独立新消息，ai_usage_log 出现两条不同 message_id 的结算记录
- [ ] eslint / vue-tsc / nest build 全部 0 错误
