# PRD-P10-AI-ATTACHMENT（AI 对话附件上传·文本类）

> 2026-09-19 ｜ Kimi ｜ 状态：已交付 CodeBuddy
> 背景：用户拍板 P10 = AI 对话附件上传，双模式（注入 + 清单自读）合并一期做全；图片/多模态另立二期（依赖 vision 模型，DeepSeek 已于 2026-08 上线 deepseek-v4-flash-vision-exp，届时加挂即可）。
> 流程：按「按规模定」出三件套（动 DB + 动契约）——本文 + ARCHITECTURE-P10-增补.md + API-P10-增补.md。
> 编号：决策 D82~~D86、规则 R82~~R87、任务 T96~T99；**零新依赖、零新 HTTP 端点、零新错误码**；AI 工具 30 不变（read_cloud_file 签名变更）；DB 加 1 列。

## 1. 背景与目标

AI 对话目前无附件能力（chat DTO 无附件字段、前端无入口、ai_message 无附件列）。本期让用户在对话中附带**文本类文件**（云盘选择或本地上传），AI 能读到附件内容。

行业事实（决定技术路线）：大模型 API **没有通用附件概念**——DeepSeek API 只收图片、文档须应用侧解析成文本注入；「解析 + 注入」是标准架构而非绕道。长文件的处理上限受模型上下文窗口（DeepSeek 系 128K）约束，故本期采用双模式：**小文件全文注入**（体验等同 DeepSeek/Kimi 网页版）+ **大文件登记清单、模型用 read_cloud_file 按需自读**（AI IDE 模式，我们的工具链现成）。

## 2. 决策

- **D82 附件数据模型**：`ai_message` 加 `attachments` JSON 列 NULL，存元信息数组 `[{ fileId, name, ext, size, chars, mode: 'inject'|'listed', path }]`。**只存元信息、不冗余附件内容**；历史轮次重组装时按 fileId 重读云盘，源文件被删 → 该附件标注失效降级（不报错、不阻断对话）。
- **D83 双模式消费**：
  - **inject（小文件全文注入）**：解析后全文拼进该条 user 消息；
  - **listed（大文件清单自读）**：不注入内容，登记进「会话可读清单」随 system 注入，引导模型用 `read_cloud_file` 分段自读；
  - 分流阈值：单文件 ≤30,000 字符 **且** 本条消息 inject 累计 ≤60,000 字符 → inject，否则 listed（截断场景见 R83）；
  - 上限：每条消息附件 ≤5 个；单文件 ≤2MB（复用 P8 口径）；会话清单最多登记 20 个。
- **D84 来源两路**：① 云盘选择（复用 P8 `FilePicker`，只读引用、不产生新文件）；② 本地上传**先落云盘 `/ai-attachments/` 固定目录留档**（自动创建；避免根目录污染；删除/回收站/配额语义完全沿用云盘，P8 导入先例）。
- **D85 预算与计费**：inject 字符纳入 P5 预算动态化——在 system/tools 之后、history 之前扣减一个 attachments 预算项；usage 按上游实际 token 实算扣积分，附件无特殊费率。
- **D86 类型白名单**：txt/md/markdown/json/js/ts/jsx/tsx/vue/css/scss/xml/yml/yaml/log/csv/html/htm/py/java/go/rs/c/cc/cpp/h/hpp/sql/sh/bat/ini/conf/toml；含 NUL 字节视为二进制拒绝；编码 UTF-8（剥 BOM）优先、GBK 回退（复用 P8 探测链，iconv-lite 既有依赖）。

## 3. 规则

- **R82 校验链**（逐附件）：本人文件 + 未删除 + 非目录 + 扩展名白名单 + ≤2MB；整条消息附件 ≤5 个。失败口径：无权/不存在 30001、类型 30012、超 2MB 30013、数量超限/其他 40001。
- **R83 注入格式**：`【附件 {name}】` 头 + fenced code block 正文；单文件 >30,000 字符但总量帽内仍有空间的边缘情形允许**截断注入**——截断处标注「（已截断，完整文件已列入可读清单，路径 {path}）」，且该文件同时进清单（模型可按需补读）。
- **R84 会话可读清单**：system 侧动态追加——「用户本会话附带文件：{path} ×N；查看内容用 read_cloud_file 按路径**分段**读取（单次 ≤2 万字符），未读前不得猜测文件内容」。清单随每轮组装刷新（新附件追加、失效标注）；清单属动态上下文，**不计入手册 2000 字帽**，但登记上限 20 条防爆。
- **R85 read_cloud_file 分页**（工具签名变更）：parameters 加 `offsetChars?: number`（默认 0）、`maxChars?: number`（默认 20000，上限 50000）；返回加 `totalChars / truncated / nextOffset`；description 写明「大文件请分段读取」。**改工具链 → 必跑 smoke:ai**（T95 触发条件表）。
- **R86 前端**：输入区回形针入口（云盘选择 / 本地上传二选一菜单）+ 待发附件 chips（名称/大小/可移除）；气泡附件行（图标 + 名称 + 模式标签：inject 无标签、listed 标「AI 按需读取」）；历史消息同渲染；附件纯展示不做跳转联动；本地选择的文件仅暂存内存，发送时才上传留档（未发送不占云盘）。
- **R87 可感知口径**：listed 附件气泡标注「大文件，AI 将按需读取」；失效附件历史气泡置灰标「源文件已删除」。

## 4. 验收标准

1. **小附件注入**：发 ≤3 万字符 md → 上游 user 消息含全文（【附件】头 + fenced），模型回复能正确引用附件内容；
2. **大文件自读**：发 8 万字符 txt → user 消息不含全文、system 含清单路径；模型**主动**调 read_cloud_file 分段读取并正确回答细节问题（smoke:ai 断言工具调用发生且 params 带分页参数）。**本期唯一不确定性**：模型不自读则调清单 prompt 措辞再测，仍不行再考虑 listed 文件首段（如前 5000 字符）预注入兜底；
3. **截断标注**：构造 >3 万字符但总量帽内可部分注入的场景 → 注入文本带截断标注且该文件进清单；
4. **校验链**：他人 fileId → 30001；exe → 30012；>2MB → 30013；第 6 个附件 → 40001；
5. **预算**：inject 后 history 预算正确扣减（DEBUG_AI=1 日志可见 attachments 项），长附件不挤爆上下文；
6. **失效降级**：发送后删除源文件 → 新一轮对话该附件标注失效、对话正常继续；
7. **前端**：chips 增删、气泡模式标签、历史渲染、失效置灰；本地上传后云盘 `/ai-attachments/` 有留档、配额 used 记账正确；
8. **回归**：`pnpm check:ai` 16/16；无附件纯文本对话行为零变化；smoke:ai 既有 F/I 用例不回归；实测消耗积分如实登记。
